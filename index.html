Coding questions

SDET coding rounds are not LeetCode-hard. They're strings, arrays and HashMaps, usually with a "now do it without the built-in method" follow-up. Tier 1 is the real exam — if you can do those cold, you'll clear most screens.

How to practise

Write it, run it, then say the time and space complexity out loud before they ask. Then delete it and write it again tomorrow. Recognition isn't recall — you need to produce these from a blank file.

Why this one project

Every junior candidate has a saucedemo POM repo. Almost none have a framework where the API sets up state for a UI test. That single idea is worth more in an interview than three separate repos, and it's the honest answer to "what have you automated?"

Writing test cases

The most common live exercise: "here's a feature, write test cases." Have a method, not inspiration.

Scenario vs case

A scenario is what you're verifying — one line, no steps. "Verify concession upload with an invalid admission number." A test case is the executable version with steps, data and an expected result. Scenarios come first and are broader; you derive several cases from one. Interviewers notice when you conflate them.

Anatomy of a case

ID · Module · Title · Preconditions · Test data · Steps · Expected result · Actual result · Status · Priority. Two rules separate good from sloppy: one case verifies one thing, and the expected result is written before you ever run it.

Write steps so someone who's never seen the product can follow them. "Login and check fees" is not a step. "Navigate to Fees > Concessions, click Bulk Upload, select valid_concessions.xlsx" is.

Coverage buckets — walk all of them

Positive / happy path · Negative and invalid input · Boundary values · Empty and null · Duplicates · Permissions and roles · Data integrity after the action · Concurrency · UI and validation messages · Integration with downstream modules.

If you produce only happy paths, that's the rejection. The negative cases are the whole test of whether you think like a tester.

Worked example — your concession upload

Positive: valid sheet, all admission numbers exist, all concession types valid → all rows applied, error array empty, amounts correct in the database.

Negative: admission number not found → row skipped, appears in error array with a reason, remaining rows still commit. Concession type not found → same. Blank admission number. Duplicate admission number within one sheet. Concession already applied to that student.

Boundary: single-row sheet · headers only · large sheet, 400+ rows · concession amount of zero · amount exceeding the fee total.

Structural: wrong file type · corrupt file · missing required column · extra unexpected column · columns reordered · numbers stored as text.

Integration: student fee statement reflects the concession · reports and dashboards update · a student promoted or withdrawn mid-upload.

If they give you something generic

Classic prompts are a login page, a lift, an ATM, a pen. First move is always the same — ask two or three clarifying questions about requirements and scope before writing anything. Then walk the buckets out loud. Candidates who start listing cases immediately score worse than candidates who scope first.

What you own — 01

Built a bulk fee-concession upload API in Spring Boot. Takes an Excel sheet keyed on admission number, applies concessions per row, isolates failures into an error array so valid rows still commit. Used by the onboarding team across 3 schools, 400+ students each. Hours down to minutes.

If pressed: the admission-number lookup is the validation. Blank or wrong number, the row fails and gets reported back.

What you own — 02

Built Excel-based bulk ingestion for IB/IGCSE timetables. Manual entry ran ~20 seconds per schedule across 1,200 schedules — roughly 7 hours. Brought it to about 1.

The pattern to name out loud: you find where onboarding is doing repetitive manual entry and turn it into a bulk path.
